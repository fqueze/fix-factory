## route-request

```
You wrote this in the factory's main box: {text}. The active requests, one per line with id and summary, are in {requestsFile}. If the text is about one of them, return its id. Otherwise it's a new request: return its kind (burning down a folder's flakiness, or fixing a try push's failures), the folder or revision, and the config (scope, platforms, constraints) the text states, leaving out anything it doesn't say. ## classify-annotation
```

sonnet · 2. First signal · inputs: `annotation`, `manifest`, `worktree`, `commit`, `bug`

```
The annotation `{annotation}` in {manifest}, in the checkout {worktree}: the oldest commit whose diff has that line is {commit}, in {bug}. That commit may be a rewrite (the .ini → .toml conversion, a mass os_version rename) rather than the one that added the skip: if so, find the one that did with `git log -S` and `git show`, and read its bug. Is it **scoping** (the test can never work in that config by design, such as a feature that config doesn't have, so it should become `run-if`) or **flakiness** (it was added because the test failed there: intermittently or every time, as a workaround for a bug, fixed since or not, or copied from another config's failure skips)? When in doubt, say flakiness: the DEBUG try push will show whether it still fails. Answer `unclear` with one sentence if neither fits.
```

## write-annotation-patches

```
Here are the skip-ifs of {folder}, each classified as scoping or flakiness: {annotations}. Write up to two commits. The first, only if a skip is scoping, turns each scoping skip into the equivalent `run-if`. The second is
```

## triage-try

sonnet · 3. Work list, 6. Verify on try · inputs: `rev`, `goal`, `tableFile`, `logsDir`

```
The result table of try push {rev} (goal: {goal}) is in {tableFile}, with the patches the push carries and the files each changes; the logs of the jobs fx-tests couldn't parse are in {logsDir}. For each failing or not-run cell, classify it as fixed, still failing, broken by patch X, unrelated pre-existing, or infra, and cite the log line it rests on. One cell per test and config: a test by its full path, a config by its job name; a test failing on several configs is several cells. ## merge-clusters
```

sonnet · 3. Work list · inputs: `clustersFile`, `logsDir`

```
The failures in {clustersFile} are clustered by exact message (numbers normalized), each cluster across every test that printed it. Turn them into work groups: one group per distinct problem, which one agent fixes with one patch, so that no two agents end up fixing the same thing.

- One test's failures in the same tasks (compare `taskIds`) are usually one problem: its first failure causes the rest. The several "leaked … until shutdown" lines one leak prints (windows at different URLs, docShells…) are one group for that test.
- Different tests share a group only when the same specific failure clearly has one cause (the same assertion from shared code, the same stack). A generic message ("Test timed out", a leaked browser.xhtml window) is never a shared cause on its own.
- One test failing in different ways (a crash on Windows, a leak on macOS) is separate groups.
- Every failure, a test in a cluster, goes in exactly one group: never list a test's failure in two groups.

When the messages don't tell, look at the failed jobs: their logs under {logsDir}/<task id>/ when present, or `fx-tests task <task id>`. Give a one-line reason for each group ("unchanged" when a cluster is kept as is).
```

## investigate-and-fix

opus · 4. Investigate and fix · inputs: `test`, `worktree`, `failureSummary`

```
Fix {test} in {worktree}, following debug-a-test-failure. The failure: {failureSummary}. Commit the fix with a message following the commit-message skill, its `r=` from the find-reviewer skill, using `Bug XXXXXXX` if the fix needs a bug of its own. When the test exposes a product bug (a leak, a race), fix the product: a test-side wait or guard that hides it is not a fix. Use "handed back" only when someone else is actively working on it. Reproduce the failure locally before changing anything; one that only shows on a platform you don't have counts as reproduced if the factory's un-skip try push shows it. Never push to try yourself (add --no-push to any mach try), and don't ask for a try push of your own: the whole stack goes to try together. The failing CI tasks' profiles (the test's `profile_<test>.json.gz` artifact) are your first evidence: read them with profiler-cli before the logs and the code, and before anything else from CI; list what each shows in \`profiles\`. Only when they can't answer what you need, commit "DEBUG -" logging as below; when your fix needs a platform you don't have, say so in `verification`: the stack's push checks it. `tryRequest` is only for a push the user asked you for in a message. If it only fails on CI and you know which race, commit a "DEBUG -" commit that logs and widens it, and stop with state "needs a try repro": the factory pushes it, with the folder's others, once the user approves, and resumes you with the results. If you can't reproduce it, stop with state "not reproduced" and say what you tried. Run builds and tests in the foreground and wait for them: your session ends when you stop, and anything still running in the background is lost. Write artifacts/evidence.md (what shows the cause, and why the fix belongs where it is) and artifacts/reproduction.md (how to reproduce it, how often it failed with and without the fix), plus artifacts/reproduction.diff if you widened the race. End with the JSON report: state, cause, the kinds of evidence (a guess from reading code says so), the reproduction, those files, how you verified the fix, a bug draft (bug-filing skill) if one is needed, and any patch yours must land after.

Other agents work in sibling worktrees of the same repository:
- Never run `git stash`: the stash is shared by every worktree. To test without your change, make a WIP commit, then `git checkout HEAD~1 -- <files>`.
- Only commit to your own branch: never move another branch (`git update-ref`, `git branch -f`, a rebase), the stack's included. The factory rewrites the stack from your commits.
- Only kill processes whose command line names your own worktree.
- Name your `profiler-cli` session and pass `--session <id>` on every call; never a bare `stop`, never `--all`.
- If a tool can't read its input (profiler-cli refusing a profile's version, say), stop: report the state "blocked" with the error, and say it in feedback. Never work around it with your own parsing scripts or another copy of the tool.
- Never submit a bug: drafts go in the report.
```

## review-patch

opus · 2. First signal, 4. Investigate and fix, 9. Review comments · inputs: `sha`, `worktree`, `report`

```
Review commit {sha} in {worktree}, diff and message together, as a demanding Firefox reviewer would. The author's report ({report}) is testimony, not evidence: spot-check its claims about the code and the test results yourself, and don't quote it. Check the message against the commit-message skill.

Look for:
- dead code, leftover instrumentation or debug logging;
- new code more complicated than the fix needs: abstractions, helpers or options used once, null checks or other defensive code with no known reason, a bigger change than the cause requires;
- comments in the code that add nothing, and padding in the commit message;
- a message claiming a mechanism the evidence doesn't show, or not saying why an apparently healthy file is edited;
- a guard on the victim's side where the leaker should have been fixed, or a test change that hides a product bug: artifacts/evidence.md must say why the product is right;
- a fix for a failure artifacts/reproduction.md doesn't show reproduced;
- a follow-up bug filed for the root cause where the direct fix wasn't attempted. "Different component", "shared helper", "needs UX input" and "design question" are not reasons on their own;
- a fix not verified by the checks it claims;
- several citations for one claim that all trace back to the same source.

Report each finding as must-fix or nit, with file and line, or return `ok`. Must-fix means the patch can't land as it is; everything else is a nit, and nits don't send the patch back. `Bug XXXXXXX` is expected at this stage (bugs are filed later): never report it.
```

## resolve-conflict

sonnet · 5. Stack, 10. Landing · inputs: `sha`, `base`, `files`

```
Rebasing {sha} onto {base} conflicts in {files}. {base} is the branch being assembled: the stack's earlier patches ("Bug XXXXXXX" in their messages until filed) on top of origin/main, so the other side may be another of the factory's patches, not a landed change: say which, with `git log`. Resolve it, keeping the intent of both sides, and give the resolved commit's sha in `commit`. ## write-test-plan
```

sonnet · 6. Verify on try, 8. Submit · inputs: `sha`, `title`, `firefoxRepo`, `investigationFile`, `files`, `keptDir`, `pushesFile`

```
Write the test plan of commit {sha} ("{title}") for its Phabricator revision: what lets a reviewer trust that the fix works. Read the commit with `git -C {firefoxRepo} show {sha}`. What its author found, and how it verified the fix, is in {investigationFile}; its notes are {files} (if that worktree was removed, the same paths are under {keptDir}). The try pushes of its request, each with what it was for and its result, are in {pushesFile}: `fx-tests try <rev> --all-jobs` shows how its tests did in one, including failures that passed on retry.

At most 5 lines of about 100 characters each, in Markdown: "- " bullets if there are several points, test names, functions, prefs and other code names in backticks. An existing test whose failures this fixes is a link to its page: [`browser_foo.js`](https://tests.firefox.dev/test.html?test=<its full path, URL-encoded>); its full path is in the investigation file. New tests stay in backticks. In this order where it applies:
- when the commit changes product or harness code, not the test itself: first, which test's failures it fixes (one short line, with its link);
- how the cause was found (the profile markers, log lines or code that show it);
- how the failure was reproduced (the race widened, chaos mode, a loop of runs), with the failure rates without and with the fix. Local runs were on this machine: name its platform (`/etc/os-release`, e.g. "locally on Ubuntu 24.04"), and the build type that reproduced it, opt or debug, and the one that didn't if both were tried;
- the try runs that show it's fixed: which platforms and jobs, how many runs, and whether they were green (check the tests' results with fx-tests first: green jobs can hide failures that passed on retry). Name a push by its Treeherder link (`[try push](https://treeherder.mozilla.org/jobs?repo=try&revision=<full hash>)`), never by a bare hash.

Only what was actually done and shown, about the commit as it is now: no line about its earlier versions, earlier pushes, or detours that didn't lead to it. If the failure was never reproduced, a platform was never run, or the try push still had failures in these tests, say so plainly. Nothing internal to how the fix was made: no agents, groups, factory, sessions or job ids, and no first person: it states facts, not what you checked or didn't. A commit that only changes test manifests: one line on the try runs that show the tests pass.
```

## write-meta-bug

sonnet · 7. Meta bug · inputs: `subject`, `worktree`, `stackFile`, `overall`, `summary`

```
Write the description of the meta bug tracking {subject}, for the reviewers of its stack (in {worktree}). Its patches, in the order they can be reviewed, with each one's sha, failure, cause and fix, are in {stackFile}. Follow the style of bug 2062142's first comment (`curl -s https://bugzilla.mozilla.org/rest/bug/2062142/comment`): one sentence on {overall}, then the patches in exactly the given order (it's the stack's), with a section title before each run of patches that need the same attention ("Skip-if annotations", "Easy test-only patches", "Test fixes that need a closer look", "Product fixes"…). Each patch is a bullet: its test in backticks and its bug, then one or two short sentences, the problem and then the fix, about 30 words in all. A patch that only changes test manifests says how many tests it re-enables (count them in `git show <sha>`), not which manifests. Markdown, nothing else: no sentence about the order or the format, no effort scores, failure counts per patch, try links or anything internal to the factory.{summary}
```

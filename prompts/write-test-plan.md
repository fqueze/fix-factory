Write the test plan of commit {sha} ("{title}") for its Phabricator revision: what lets a reviewer trust that the fix works. Read the commit with `git -C {firefoxRepo} show {sha}`. What its author found, and how it verified the fix, is in {investigationFile}; its `alsoFixes`, when there, are other tests this commit fixes too (their own fix was dropped as covered by it, with how that was checked): each is a link on the first line along with the commit's own test, and gets its reproduction and verification too; its notes are {files} (notes written before the item had a folder of its own are at the same paths in {worktree}, or under {keptDir} once that worktree was removed). The try pushes that had this commit, each with what it was for, its result, `thisVersion` (false: it had an earlier version of the commit), and `runs` (where its tests ran in it, per job: runs, passed, passed on retry, failed, read by the factory with fx-tests) and `failedJobs` (the Treeherder links of the jobs where they failed), are in {pushesFile}; cite no other push, and say nothing about try if it is empty. What you say about try (platforms, build types, variants, how many runs, their results) comes from `runs` and nothing else: a job not listed there didn't run the test, whatever the push selected.

Reviewers read it before the diff and the commit message, and skim it: it says only what they can't see there, in at most 3 lines of about 100 characters each, in Markdown: "- " bullets if there are several points, test names, functions, prefs and other code names in backticks. A test's link to its page is [browser_foo.js](https://tests.firefox.dev/test.html?test=<its full path, URL-encoded>), with no backticks inside the brackets (Phabricator doesn't render code in link text); its full path is in the investigation file. New tests stay in backticks. In this order where it applies:
- where the failures it fixes were seen, when that says something: when `fx-tests test <its path>` shows them on tests.firefox.dev, the test's link and the failure in a few words, plus the folder's link ([<folder>/](https://tests.firefox.dev/tests.html?path=<the folder, URL-encoded>)) when the same failure hit other tests of it; when it was only seen on try, say so, with the job's link and its platform (a VM says so), and how often it happens in CI as unknown; otherwise only when the commit changes product or harness code, not the test or its manifest, the test in backticks. Never what central doesn't show (no "not seen in CI", no "its central failures are a different one"): nobody looked for long enough to say it;
- the evidence that shows the cause, only with a link a reviewer can open: each profile finding's `permalinks` in the investigation file, a profile marker linked as [the marker](<its permalink>). Evidence with no link (a local log, code reading) is left out;
- how the failure was reproduced and the fix verified, naming what was run as a reviewer would type it (`--verify`, `--repeat 20`, `MOZ_CHAOSMODE=0xfb`), and a widening in words (a 150 ms delay before a named function): an env var, switch or scratch test that only exists in a patch the reviewer doesn't get is left out, with the failure rates without and with the fix. Local runs were on this machine: name its platform (`/etc/os-release`, e.g. "locally on Ubuntu 24.04"), and the build type that reproduced it, opt or debug, and the one that didn't if both were tried;
- the try runs that show it's fixed: which jobs, how many runs, and whether they passed, all from `runs` (its `passedOnRetry` counts runs that failed then passed: green jobs can hide them). Name a push by its Treeherder link (`[try push](https://treeherder.mozilla.org/jobs?repo=try&revision=<full hash>)`), never by a bare hash, and a failure in it by its job's link from the push's `failedJobs`.

Nothing the commit message or the diff already says: no restating the cause or the bug, no describing the change (what the test now waits for or checks). No filler words ("opt build", not "full opt build"). Nothing a reviewer already knows: no platform the test only runs on, no "before the fix it failed" that the failure already says. A push with no runs of the test is left out, and nothing is said about what a tool could or couldn't show. Only what was actually done and shown, about the commit as it is now: no line about its earlier versions, earlier pushes, or detours that didn't lead to it. Nothing about what wasn't done: no platform, build type or push that wasn't run, nothing "untested" or "not confirmed"; a reviewer reads those as doubt, and what was run speaks for itself. The one exception: a try push that still had failures in these tests, said plainly. Nothing internal to how the fix was made: no agents, groups, factory, sessions or job ids, and no first person: it states facts, not what you checked or didn't. A commit whose effect is plain from its diff (one that only changes test manifests, or stops running a test in a case): one line on the try runs that show the tests pass.

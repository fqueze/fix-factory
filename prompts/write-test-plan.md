Write the test plan of commit {sha} ("{title}") for its Phabricator revision: what lets a reviewer trust that the fix works. Read the commit with `git -C {firefoxRepo} show {sha}`. What its author found, and how it verified the fix, is in {investigationFile}; its notes are {files} (if that worktree was removed, the same paths are under {keptDir}). The try pushes of its request, each with what it was for and its result, are in {pushesFile}: `fx-tests try <rev> --all-jobs` shows how its tests did in one, including failures that passed on retry.

At most 5 lines of about 100 characters each, in Markdown: "- " bullets if there are several points, test names, functions, prefs and other code names in backticks. In this order where it applies:
- how the cause was found (the profile markers, log lines or code that show it);
- how the failure was reproduced (the race widened, chaos mode, a loop of runs), with the failure rates without and with the fix. Local runs were on this machine: name its platform (`/etc/os-release`, e.g. "locally on Ubuntu 24.04"), and the build type that reproduced it, opt or debug, and the one that didn't if both were tried;
- the try runs that show it's fixed: which platforms and jobs, how many runs, and whether they were green (check the tests' results with fx-tests first: green jobs can hide failures that passed on retry). Name a push by its Treeherder link (`[try push](https://treeherder.mozilla.org/jobs?repo=try&revision=<full hash>)`), never by a bare hash.

Only what was actually done and shown, about the commit as it is now: no line about its earlier versions, earlier pushes, or detours that didn't lead to it. If the failure was never reproduced, a platform was never run, or the try push still had failures in these tests, say so plainly. Nothing internal to how the fix was made: no agents, groups, factory, sessions or job ids, and no first person: it states facts, not what you checked or didn't. A commit that only changes test manifests: one line on the try runs that show the tests pass.

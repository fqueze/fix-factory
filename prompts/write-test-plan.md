Write the test plan of commit {sha} ("{title}") for its Phabricator revision: what lets a reviewer trust that the fix works. Read the commit with `git -C {firefoxRepo} show {sha}`. What its author found, and how it verified the fix, is in {investigationFile}; its `alsoFixes`, when there, are other tests this commit fixes too (their own fix was dropped as covered by it, with how that was checked): each is a link on the first line along with the commit's own test, and gets its reproduction and verification too; its notes are {files} (if that worktree was removed, the same paths are under {keptDir}). The try pushes that had this commit, each with what it was for, its result, `thisVersion` (false: it had an earlier version of the commit), and `runs` (where its tests ran in it, per job: runs, passed, passed on retry, failed, read by the factory with fx-tests), are in {pushesFile}; cite no other push, and say nothing about try if it is empty. What you say about try (platforms, build types, variants, how many runs, their results) comes from `runs` and nothing else: a job not listed there didn't run the test, whatever the push selected.

At most 5 lines of about 100 characters each, in Markdown: "- " bullets if there are several points, test names, functions, prefs and other code names in backticks. An existing test whose failures this fixes is a link to its page: [browser_foo.js](https://tests.firefox.dev/test.html?test=<its full path, URL-encoded>), with no backticks inside the brackets (Phabricator doesn't render code in link text); its full path is in the investigation file. New tests stay in backticks. In this order where it applies:
- when the commit changes product or harness code, not the test itself: first, which test's failures it fixes (one short line, with its link);
- how the cause was found (the profile markers, log lines or code that show it);
- how the failure was reproduced (the race widened, chaos mode, a loop of runs), with the failure rates without and with the fix. Local runs were on this machine: name its platform (`/etc/os-release`, e.g. "locally on Ubuntu 24.04"), and the build type that reproduced it, opt or debug, and the one that didn't if both were tried;
- the try runs that show it's fixed: which platforms and jobs, how many runs, and whether they passed, all from `runs` (its `passedOnRetry` counts runs that failed then passed: green jobs can hide them). Name a push by its Treeherder link (`[try push](https://treeherder.mozilla.org/jobs?repo=try&revision=<full hash>)`), never by a bare hash.

A push with no runs of the test is left out, and nothing is said about what a tool could or couldn't show. Only what was actually done and shown, about the commit as it is now: no line about its earlier versions, earlier pushes, or detours that didn't lead to it. Nothing about what wasn't done: no platform, build type or push that wasn't run, nothing "untested" or "not confirmed"; a reviewer reads those as doubt, and what was run speaks for itself. The one exception: a try push that still had failures in these tests, said plainly. Nothing internal to how the fix was made: no agents, groups, factory, sessions or job ids, and no first person: it states facts, not what you checked or didn't. A commit that only changes test manifests: one line on the try runs that show the tests pass.

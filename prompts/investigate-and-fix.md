Fix {test} in {worktree}, following debug-a-test-failure. The failure: {failureSummary}. Commit the fix with a message following the commit-message skill, its `r=` from the find-reviewer skill, using `Bug XXXXXXX` if the fix needs a bug of its own. The commits of one failure's fix share one bug: a commit added later for the same failure uses the bug its first commit already has (often the test's intermittent tracking bug), never a new one beside it. When the test exposes a product bug (a leak, a race), fix the product: a test-side wait or guard that hides it is not a fix. When a test has to wait, it waits for the event, promise or mutation that says the thing happened. Polling (`waitForCondition` and the like, timers) hides the race behind a timeout: only in a test that already waits that way, or with a brief comment saying nothing better can be waited for. A wait for animation frames says in a comment what it waits for (typically the tested code itself waiting for a frame). Every wait or ordering change says why in the code or the message, in words a reviewer understands without your investigation. One commit per fix, its skip-if removals included; never keep or narrow a skip-if without the try failure and profile showing it still fails, and why that failure isn't fixed. Use "handed back" only when someone else is actively working on it. Reproduce the failure locally before changing anything; one that only shows on a platform you don't have counts as reproduced if the factory's un-skip try push shows it. Never push to try yourself (add --no-push to any mach try), and don't ask for a try push of your own: the whole stack goes to try together. The failing CI tasks' profiles (the test's `profile_<test>.json.gz` artifact) are your first evidence: read them with profiler-cli before the logs and the code, and before anything else from CI; list what each shows in \`profiles\`. Only when they can't answer what you need, commit "DEBUG -" logging as below; when your fix needs a platform you don't have, say so in `verification`: the stack's push checks it. `tryRequest` is only for a push the user asked you for in a message. If it only fails on CI and you know which race, commit a "DEBUG -" commit that logs and widens it, and stop with state "needs a try repro": the factory pushes it, with the folder's others, once the user approves, and resumes you with the results. If you can't reproduce it, stop with state "not reproduced" and say what you tried. Run builds and tests in the foreground and wait for them: your session ends when you stop, and anything still running in the background is lost. Write artifacts/evidence.md (what shows the cause, and why the fix belongs where it is) and artifacts/reproduction.md (how to reproduce it, how often it failed with and without the fix), plus artifacts/reproduction.diff if you widened the race. End with the JSON report: state, cause, the kinds of evidence (a guess from reading code says so), the reproduction, those files, how you verified the fix, a bug draft (bug-filing skill) for each commit that needs a bug of its own (separate fixes, separate bugs), and any patch yours must land after.

Other agents work in sibling worktrees of the same repository:
- Never run `git stash`: the stash is shared by every worktree. To test without your change, make a WIP commit, then `git checkout HEAD~1 -- <files>`.
- Only commit to your own branch: never move another branch (`git update-ref`, `git branch -f`, a rebase), the stack's included. The factory rewrites the stack from your commits.
- Only kill processes whose command line names your own worktree.
- Name your `profiler-cli` session and pass `--session <id>` on every call; never a bare `stop`, never `--all`.
- If a tool can't read its input (profiler-cli refusing a profile's version, say), stop: report the state "blocked" with the error, and say it in feedback. Never work around it with your own parsing scripts or another copy of the tool.
- Never submit a bug: drafts go in the report.
